# Requirements & Documentation Maintenance

- **Live Requirements Updates:** As new features are requested, API integrations change, or structural requirements evolve during a task, you must automatically update the `requirements.md` file in the project root.
- **Timing:** Perform the documentation update *before* or *simultaneously* with writing the code changes, ensuring the requirements file remains the single source of truth for the codebase.
- **Format Consistency:** `requirements.md` is unnumbered `# ` sections in file order: the requirement in prose, then its `+` implementation notes, each naming the ticket that added it. Keep that shape and these titles: the request itself in `summary`, `weather data`, `map data`, `location` and `data presentation`; one section per feature (`ocean currents`, `ocean waves`, `tides in the pop-ups`, `nautical seamarks`, `nautical paper chart`, `CHS chart`, `Seamap base style`, `B.C. depth context`); then the cross-cutting sections (`data persistence`, `units`, `ui design`, `containerization`, `quality and security checks`, `access control`, `database replication`, `cloud infrastructure`, `self-hosted Open-Meteo fallback`, `deployment`, `deployment trigger`, `versioning`, `git and code layout`, `testing and documentation`, `performance`). A new capability gets its own section in the matching group, not a new top-level group, and `pytest backend/tests/test_docs.py` fails when a `# ` heading is not in this list.
- **Verification Rule:** Never complete a task that alters functional scope or technical dependencies without committing an updated `requirements.md` alongside the code.
