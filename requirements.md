# summary
create a standalone application that shows wind predictions on a map

# weather data
the weather data should come from open source api sources (ie. meteo, etc.) and the data should be displayed in a map

provide dropdown for weather model options with Open-Meteo as the default option

the default location should be the user's current location. if not able to determine current location, default to Oak Harbor, Washington, are 48.2939° N, 122.6064° W

The app opens centred on the current location, or on the first saved location when geolocation is unavailable, with **no** details pop-up and no highlighted marker: a location pop-up appears only when the user clicks a barb, clicks a saved-location marker, chooses a location in the saved-locations list or adds one from the search box (SCRUM-248). Deleting the selected location clears the selection instead of selecting the first remaining one.

the application should be able to show multiple locations at once, each marked with an icon, and the user should be able to click on an icon to see the weather predictions for that location

the web ui should have a text box allowing users to add locations - the locations should be verified and converted to lat/long before adding to location database

provide a button to list saved locations with minus sign buttons for removal

wind data should include wind speed, wind gust, and wind direction

cache weather data with 30min TTL
+ Saved locations are cached in `weather_cache` keyed by (location_id, model, timezone).
+ Ad-hoc map points (`GET /api/weather/point`, location_id 0) are cached in `point_weather_cache` keyed by (lat, lon rounded to 2 decimals, model, timezone), so different points never share a cached forecast (SCRUM-88).
+ The timezone is part of both keys (SCRUM-92) because forecast times are returned in the requested timezone; changing the timezone fetches a new forecast instead of serving one cached for another timezone. Cached responses always carry the requested point's name and coordinates. Old (0, model) rows in `weather_cache` are no longer read.
+ A second provider (SCRUM-106): `nws_ndfd` is the NOAA NWS NDFD gridpoints API at `https://api.weather.gov`, offered like a model for saved locations and ad-hoc points. `/points` maps a coordinate to a forecast office and grid cell and is cached for good in `nws_grid_cache` (no expiry, because a coordinate's grid does not move), so only the first request for a point pays that call; `/gridpoints` is fetched per hour and held by the forecast cache for the same 30 minutes as every other model. Each of the 16 slices takes the value of the NDFD period that contains its start instant, so a 6-hour or 9-hour period repeats across two or three slices instead of being averaged. NDFD is the US only: a point outside it answers 404 with a fixed message, and `/api/weather/all` skips that location so the map shows "No data" rather than a forecast from a different provider. It cannot serve the wind grid (one request per point), so the grid, the gradient and the currents stay on Open-Meteo. Missing NDFD fields stay null, humidity included — the field is nullable now and still not rendered. NWS asks for an identifying User-Agent (an empty one is answered with 403, measured 2026-11-25), and a 5xx/429 is retried twice honouring `Retry-After` before it becomes a 502.

# map data
use an open-source map library (e.g., Leaflet.js with OpenStreetMap or CartoDB)
+ Support CARTO API Key via CARTO_API_KEY environment variable or in-app settings modal (removes CARTO's "API KEY REQUIRED" watermark).
+ Provide OpenStreetMap Dark mode as default keyless, watermark-free base layer.

get and use api key for map library

# location
the user should be able to select a location and see the weather predictions for that location

Typing in the search box queries https://geocoding-api.open-meteo.com/v1/search?name=... and displays a dropdown matching name, admin1 (state/region), country, allowing one-click addition with exact coordinates.

# data presentation
show 16 data points for each location starting from now and every 3 hours after that for the next 48 hours based on the user selected timezone with a default of Pacific

clicking on location should show;
+ location name
+ lat/long
+ wind speed
+ wind gust speed
+ wind direction - both cardinal (e.g. SW) and degrees
+ temperature

Wind Grid Overlay (SCRUM-86, SCRUM-89): A continuous grid of wind barbs covering the entire visible map viewport, not just saved locations.
+ Grid density: approximately one barb per 80px at the current zoom level; grid dimensions (cols × rows) are computed from the map bounds and pixel size on each pan/zoom.
+ Data source: `GET /api/weather/grid` backend endpoint, which accepts a bounding box, grid dimensions and optionally a forecast hour, fetches the wind from Open-Meteo in batched requests of at most 150 points each (SCRUM-192: a large view used to build a ~16 KB URL that Open-Meteo answered with 414, so the view is split into chunks; SCRUM-194: the grid is capped at 20 × 20 = 400 points because Open-Meteo charges one call per point against 600 per minute, and 30 × 30 = 900 could never fit), and caches each grid point per hour for 30 minutes (same TTL as location weather). Since SCRUM-166 one forecast-hour request stores **every hour of that UTC day** it already downloaded, so a multi-hour range reads the rest of the day from SQLite instead of repeating the upstream call (a same-day range costs one request, a cross-midnight range one per day). No additional CARTO tile API calls are incurred — barbs are DOM elements, not tiles.
+ A click on the refresh button (SCRUM-113) is the only thing that sends `refresh=true`, and the server decides what that means: a cached row is refetched only when its `cached_at` predates the model's newest **published** run (`available_utc` from SCRUM-256, or the derived cycle for the models without a metadata file), so a repeat click, a stale tab or a hand-written parameter costs no upstream call. A grid refresh treats only those older points as misses and asks Open-Meteo for them alone; the response shape, the hour keying and the quota 503 are unchanged.
+ The refresh button in the top bar (SCRUM-113) is enabled only while a run newer than the data on screen exists — `data_as_of < available_utc` — where `data_as_of` is the newest server `cached_at` among the marker forecasts, never the browser clock. It carries its own visibility rule (visible at every width, unlike the `lg`-only model dropdown), shows `aria-busy` and a spinner while the click's responses are in flight, and explains itself on hover (SCRUM-257): a styled hint under the icon reads `Latest run already loaded` / `Next run available ~20:05`, using the same `formatRunTime` string as the footer, says `Next run time unknown` when the model publishes no next run, `Waiting for the first forecast` before any response has landed, `Refresh data now` while enabled and `Refreshing…` during the click. The hint lives on a wrapper because a disabled button takes no pointer events or focus, and the same sentence is always in a screen-reader-only span referenced by `aria-describedby`. A 30-second tick re-evaluates the gate, so the button wakes up when a run lands without a reload. A failure leaves the old data on screen with a short message and the button usable; the selected forecast hour and an open pop-up are preserved.
+ A pop-up's own auto-pan does not refresh the grid (SCRUM-251): Leaflet pans the map when a clicked barb's pop-up would cross an edge, and refetching there replaced the points, rebuilt every marker and closed the pop-up. That `moveend` is skipped (`autopanstart` marks it, `dragstart` and `zoomend` clear the mark), so the pop-up stays open and the next real pan, zoom or view change refreshes as usual.
+ Pop-up placement (SCRUM-252): the saved-location, wind-barb and current-chevron pop-ups bind with shared options (`utils/popupPlacement.ts`) — auto-pan, `keepInView`, 12 px edge padding and 88 px reserved at the top for the zoom control and the floating notices. When even a full pan cannot fit the card (the tide block makes it tall), `placePopupInView` nudges it inside with margins and hides the tip once the move exceeds 16 px, so no tip points at the wrong place. Placement runs on `popupopen`, again when the tide block arrives, and after Leaflet's auto-pan settles.
+ Barb style (SCRUM-89): the same meteorological wind barb drawing as the saved-location markers (staff points toward the wind direction; 50 kt pennants, 10 kt full barbs, 5 kt half barbs; calm < 2 kt renders as a circle). Grid barbs use the same temperature color scale; speed is indicated by the number of barbs. If a point has no temperature, its barb falls back to green (#4ade80). No legend is shown.
+ `GET /api/weather/grid` returns `temperature_f` per point (Open-Meteo current `temperature_2m`, converted to °F and rounded to 1 decimal, same as the saved-location forecast). `grid_weather_cache` gains a nullable `temperature_f` column, added automatically to existing tables; cached rows without a temperature are refetched.
+ Gusts (SCRUM-210): each grid point also carries `wind_gust_knots` (Open-Meteo `wind_gusts_10m`, in the same request, so no extra upstream call), stored in a nullable column of the same cache and kept when a point is served from it. A model that has no gust for a point leaves the field null rather than reporting a gust of 0 kt, and the cache tables are recreated by the schema bump (4 → 5) as usual.
+ Missing values (SCRUM-225): Open-Meteo's null wind speed, direction or temperature is never turned into 0 kn, 0° or 32 °F. A grid point missing any of the three returns null for all three, so no barb is drawn for it, the colour gradient leaves it and every interpolation cell that touches it unpainted, and its pop-up says "No data". A saved location without wind draws a no-data marker instead of a calm barb, and its pop-up says "No data". When every point in the view is missing and a wind layer is on, the map shows "No data from <model> for this area". All-missing grid and forecast frames are returned but not cached, so the next request retries Open-Meteo.
+ Selected grid point (SCRUM-89, SCRUM-126): the clicked barb is drawn larger with a white highlight ring, and its pop-up shows the same values, because both come from the one grid response.
+ Barb click (SCRUM-88, SCRUM-126, SCRUM-210): clicking a barb clears the saved-location selection, highlights it and opens a small pop-up at the barb with that point's wind speed, gust, direction (barb, cardinal or whole degrees, following the user's direction display) and temperature in the user's units. The values come from the grid response already on the map, so the click makes no request. Saved-location selection behaviour is unchanged: clicking one restores its highlight and pop-up.

Forecast time (SCRUM-115): the API and the map layers can render any hour in the forecast window; the app itself still opens on current conditions because the control that picks an hour is SCRUM-127.
+ `GET /api/weather/grid`, `/api/weather`, `/api/weather/all` and `/api/weather/point` accept an optional `time`: an ISO 8601, hour-aligned instant with an offset. It must be between the current hour (rounded down) and the selected model's horizon; anything naive, misaligned, past or beyond that horizon is a 422 whose message names the limit. Omitting `time` keeps the previous behaviour exactly: live `current` values, no `valid_time`, grid points with `time: null`.
+ The window is per model, from `MODEL_METADATA` in `backend/app/config.py` (each entry names the Open-Meteo doc page its cadence and horizon come from): 7 days for `best_match` (Open-Meteo's documented default for the composite), 15 for `ecmwf_ifs` (ECMWF IFS HRES 9 km), 15 for `ecmwf_aifs025_single` (ECMWF AIFS, AI), 16 for `gfs_seamless`, 3.5 for `ncep_rrfs_north_america`, 10 for `gem_seamless` and 7.5 for `icon_seamless`. `test_forecast_time.py` asserts those values directly since the static table was removed (SCRUM-232).
+ ECMWF is the 9 km HRES grid served as `ecmwf_ifs` (SCRUM-226); the old `ecmwf_ifs04` id returned nulls from Open-Meteo. The retired id is answered as `ecmwf_ifs` for one release (`MODEL_ALIASES`), so a cached frontend gets ECMWF values instead of a 422.
+ Environment Canada's model is `gem_seamless` (SCRUM-228), which blends the 12-hourly global GEM with the 6-hourly regional RDPS and HRDPS runs, so it covers the globe without regional-coverage handling; Open-Meteo caps it at 10 days (240 h), not the 16 days the static table used to claim.
+ ECMWF's AI model is `ecmwf_aifs025_single` (SCRUM-227), the 0.25° AIFS grid with 6-hourly cycles and a 15-day horizon; Open-Meteo interpolates its native 6-hourly steps to hourly. It carries no wind gusts, so the gust fields stay null and the pop-ups omit the gust line instead of showing a calm value.
+ NOAA's RRFS is `ncep_rrfs_north_america` (SCRUM-231), labelled **"RRFS (North America)"**: the 13 km North American grid, hourly values on 6-hourly cycles (00/06/12/18 UTC) and an **84-hour horizon**. Open-Meteo returns nulls after the last published hour (79 h on 2026-11-26), which are no data, never calm wind or a 502. Coverage is North America only: a batch containing one point outside the domain fails with `400 {"reason": "No data is available for this location"}`, so the grid halves the batch and retries each half, keeping the covered points and treating a point that still fails as no data (the SCRUM-229 decision; the published grid box misclassified island and edge points, so no polygon is used). The split is bounded per chunk (`COVERAGE_SPLIT_MAX_REQUESTS`). The point forecast turns the same 400 into an empty series with a null current point, so a saved location or barb outside the domain shows "No data" and is not cached; no fallback model is mixed into the view. The selector always offers RRFS, labelled with its region, rather than disabling itself while a view straddles the edge.
+ `GET /api/weather/models` returns each model's `update_hours`, `update_cycles_utc`, `horizon_hours`, `last_run_utc` and `next_run_utc`. Run times are derived from the cycle hours (00/06/12/18 UTC for the six-hourly models, every hour for `best_match`) because Open-Meteo's Forecast API does not return the model run time; they are labelled as the model run, not the request time.
+ Published run times (SCRUM-256): `GET /api/weather/models/{model}/availability` returns `run_utc`, `available_utc` and `next_available_utc` from `https://api.open-meteo.com/data/<meta id>/static/meta.json` (`last_run_initialisation_time`, `last_run_availability_time`, plus `update_interval_seconds` for the next one), or nulls when the model has no single upstream run. Only `gfs_seamless` (`ncep_gfs025`), `ecmwf_ifs` (`ecmwf_ifs025`), `ecmwf_aifs025_single` and `icon_seamless` (`dwd_icon`, the global run on purpose) have one: `best_match` and the seamless blends are composites, and GEM's metadata files have been frozen since 2026-05-26 even though its forecast still updates, so those keep the derived cycle. The fetch has a 3 s timeout and no retries, and its answer (a failure included) is cached in memory for 10 minutes, so a freeze hint never delays a forecast or hammers a broken file. A metadata outage, a 404 or a malformed body is an empty answer, never an error.
+ Caches are keyed by hour: `grid_weather_cache.hour` (`'current'` for live values), and the forecast caches key on `(…, timezone, hour)`. `SCHEMA_VERSION` is 3; the cache tables are recreated on upgrade because they only hold refetchable data.
+ The frontend threads it as `validTime`: `useWindGrid(map, model, enabled, validTime)` and `useAllWeather(model, timezone, validTime)` send `time` and refetch when it changes, and `MapView` accepts `validTime`. The selector added by SCRUM-127 is what sets it.
+ Gone with the drawer (SCRUM-89, SCRUM-90, SCRUM-97): the per-slice cards, the "Now" slice, whole-degrees-true labels and the humidity field. The API still returns `humidity`, `wind_direction_deg` and the 16-slice `forecast` array unchanged, and `/api/weather/point` still names a point "48.78°N, 121.94°W".

# ocean currents (SCRUM-96)
show ocean and water currents on the map alongside the wind, with chevrons pointing where the water flows

+ Data source: Open-Meteo Marine API (`https://marine-api.open-meteo.com/v1/marine`), variables `ocean_current_velocity` and `ocean_current_direction`, provided by MeteoFrance SMOC (Copernicus Marine): global ~0.083° (~8 km), hourly, 10-day forecast, updated once a day. Currents are independent of the selected weather model — one field, with its own 240-hour horizon. Each returned cell centre is also checked against the Open-Meteo Elevation API (`https://api.open-meteo.com/v1/elevation`, metres above sea level) before a chevron is drawn, because the Marine land mask is coarser than the chart (SCRUM-238).
+ Velocity is requested in knots (`wind_speed_unit=kn`), matching the wind endpoints. `ocean_current_direction` is where the water flows **towards** (0° north, 90° east), so a chevron rotates by the value directly instead of the 180° flip wind barbs need.
+ `GET /api/currents/grid` takes `min_lat`, `max_lat`, `min_lon`, `max_lon`, `cols`, `rows` and an optional `time`, and returns `{points, time}`. Nodes with no current (land, or outside the model domain) are absent, never zeroed. Each point carries the coordinates of the Marine model cell its value came from (SCRUM-238), not the requested map point, and points that snap to the same cell are returned once. Cells whose centre is above `LAND_ELEVATION_THRESHOLD_M` (0.5 m) are land and are dropped, so the coarse Marine mask cannot put a chevron on a narrow island; one batched elevation lookup covers the unique cells of a request, and if it fails the values are kept rather than hiding real water. `time` is validated against the 240-hour current horizon, not the weather model's horizon.
+ `GET /api/currents/point` takes `lat`/`lon` and returns up to 48 hourly values from the current hour (empty for an inland point), for the chevron pop-up.
+ `grid_currents_cache` stores velocity and direction per (rounded lat, lon, hour) with the 30-minute TTL. A row with null values records "checked, no current", so an inland view is not refetched on every pan, and one forecast-hour request stores every hour of that UTC day (the wind grid's pattern). Rows also store `cell_lat`/`cell_lon` and a cache hit returns them, so a cached response places chevrons identically; a cell found on land is stored as an empty row, so its elevation is not looked up again. Schema v6 adds the cell columns and v7 recreates the caches so rows cached before the land test are re-checked (SCRUM-238).
+ Marine calls go through the shared Open-Meteo client, so retries, `Retry-After` and the 429 → 503 `open_meteo_quota_exhausted` response with `reset_at` behave exactly as on the wind grid.
+ Frontend layer (SCRUM-99): chevrons are DOM markers drawn from the same grid density as the wind barbs (one point per 80 px, capped at 120 chevrons per viewport). `WaterCurrentChevron` draws one chevron below 0.5 kt and two above it, with the tier colours and heavier stroke from `utils/currentTiers.ts`; the glyph rotates by the flow direction directly. Every glyph is drawn over a dark rim (`CURRENT_TIER_OUTLINE`) and all fills are opaque (SCRUM-237: pale ice, cyan, white and pink), so each tier clears the 3:1 graphics floor against every base water colour and against the wind gradient at 0 to 25 kn at both overlay opacities; the legend swatches carry the same rim. A vitest test enforces it from the tier table and `COLOR_STOPS`. `useCurrentGrid` fetches `/api/currents/grid` for the visible bounds at the hour selected in the forecast time bar and aborts a superseded request. It hides the layer (no error) when the hour is past the 240-hour current horizon or the request fails, because the wind timeline reaches further than the current model. Clicking a chevron opens a pop-up with the speed in the user's speed unit, the direction as compass point and degrees, the source and the selected hour, with no extra request. The layer reads the persisted `water_currents_visible` setting, default off. Its `Water Currents` toggle in Map Settings (SCRUM-100) is independent of both wind layers and survives a reload, and a compact key at the map's top-left lists the four tiers with their ranges in the user's speed unit, drawn from the same `CURRENT_TIERS` table as the glyphs so the two cannot drift. The key is a card rather than a strip because the wind colour legend already owns the full width above the attribution and all three layers can be on at once. The Water Currents toggle carries a note that the model's cells are about 6 to 9 km, so narrow waters such as Port Susan may show no current (SCRUM-238).

# ocean waves (SCRUM-233, SCRUM-234)

+ Values come from Open-Meteo Marine (`wave_height`, `wave_direction`, `wave_period`, `best_match`), hourly for 240 h, independent of the selected weather model and through the same shared client as the currents (retries, 429 → `503 open_meteo_quota_exhausted` with `Retry-After`). Heights stay in metres; the frontend converts to feet. `wave_direction` is where waves come **from** (meteorological, like wind), so an arrow adds 180° to show travel.
+ `GET /api/waves/grid` takes `min_lat`, `max_lat`, `min_lon`, `max_lon`, `cols`, `rows` and optional `time`, and returns `{points, time}`. The Marine API does not return null over land: an inland request is snapped to its nearest sea cell (east of Seattle answered for a cell about 18 km away), so a value farther than half the requested grid spacing (floor 3 km) from its node is treated as no waves and dropped, never drawn over land. A node on the water is placed at the model cell, points sharing a cell are returned once, and dropped nodes are cached as empty rows so panning inland does not refetch them. Every returned **cell** is also tested against a bundled 1 km GLOBE land mask (SCRUM-263), because the wave models' own land mask is about 8 km wide and puts sea cells on narrow islands: the Whidbey Island case drew arrows over the island. The asset is `backend/app/data/land_mask_1km.bin.z`, bit-packed one bit per cell and zlib-compressed (1,282,678 bytes on disk, 116,640,000 decompressed, about 125 MB resident, standard library `zlib` only), rebuilt by `scripts/build-land-mask.py` from the `global-land-mask` package (build-time only; GLOBE v1.0, NOAA/NCEI, not subject to US copyright, citation doi:10.7289/V52R3PMS). A cell on land is dropped and cached as an empty row like an inland node; a missing or unreadable asset fails open and only logs a warning. `time` is validated against the 240-hour wave horizon (`ocean wave horizon`), not the weather model's.
+ `GET /api/waves/point` takes `lat`/`lon` and returns up to 48 hourly values from the current hour (empty for an inland point), using the fixed 5 km tolerance, for the wave pop-up.
+ Cache: `grid_waves_cache` (schema 10), keyed by `(rounded lat, lon, hour)`, one hourly request storing every hour of that UTC day, with the 30-minute TTL. A NULL height means "checked, no waves".
+ Frontend layer (SCRUM-234): the `Ocean Waves` toggle in Map Settings is persisted as `water_waves_visible`, off by default, and independent of both wind layers and the currents, so arrows and chevrons can be shown together because their shapes differ. `useWaveGrid` fetches `/api/waves/grid` for the visible bounds at the hour selected in the forecast time bar, aborts a superseded request, samples a dense view down to 120 arrows, hides without an error past the 240-hour wave horizon, and fails silently except for the quota warning. `WaveArrow` draws an arrow pointing where the waves travel (`direction_deg + 180`, since the API names where they come from), sized and coloured by `utils/waveTiers.ts` (0–1, 1–2, 2–4 and over 4 m; 0–3, 3–6, 6–13 and over 13 ft) over a dark rim so the glyph reads on light bases and over the wind gradient. A click opens a pop-up with the height in feet or metres, the period, the direction the waves come from, the Marine source and the selected hour, then the next 48 hours from `/api/waves/point`, loaded on open and cached per rounded point (a failure is not cached and leaves the summary intact). One `MapLegend` at the map's top-left replaces the separate currents and waves keys (SCRUM-263): it always shows three wind barb examples (5, 15 and 35 kt, i.e. a half barb, a full plus a half, and a pennant plus a full plus a half) in one neutral grey because on the map a barb's colour is the temperature, with the note `colour = temperature`; it adds a currents row of chevron glyphs and a waves row of arrow glyphs, each with its tier ranges in the user's speed unit or in feet/metres, only while those layers are on. Arrows are drawn at 28/34/40/46 px (up from 20/24/28/32) and the smallest keeps a 32 px hit area with the glyph centred in it. Arrow markers are DOM content of the map, so image and range exports capture them; the export footer adds `Wave data: Copernicus Marine (via Open-Meteo)` only while the layer is on.

# tides in the pop-ups (SCRUM-195)
show the tide height and the nearest high and low in the saved-location and wind-point pop-ups

+ Data source: Open-Meteo Marine API `sea_level_height_msl`, the same MeteoFrance SMOC (Copernicus Marine) series as the currents: global ~0.083° (~8 km), hourly, 10-day forecast, updated once a day. The value is sea level **including tides** referred to global mean sea level, not a chart datum, and Open-Meteo calls it unsuitable for navigation; every response names `datum: "msl"` and the block repeats `above MSL` and `Not for navigation`. Tides are independent of the selected weather model and use the 240-hour current horizon.
+ `GET /api/tides/point` takes `lat`, `lon` and an optional `hour` (same ISO 8601, hour-aligned validation as the currents; past, naive or beyond the horizon is a 422) and returns `{latitude, longitude, datum, unit, hour, points, last_extreme, next_extreme}`. `points` is the three-day hourly series in metres; an inland point or one outside the model returns `points: []` and no extremes. `last_extreme` is the nearest high or low at or before the selected hour, `next_extreme` the first one after it and `next_extreme_after` the one after that (SCRUM-250), each `{type: "high"|"low", time, height_m}`.
+ One request covers the previous, the selected and the following UTC day, and every hour of it is stored in `tide_point_cache`, keyed by (rounded lat, lon, hour) with the 30-minute TTL. A row with a null height records "checked, no water here", so an inland pop-up is not refetched. Schema v8 adds the table; the upgrade recreates the caches and keeps saved locations.
+ Extremes are derived server-side by neighbour comparison — a sample above both neighbours is a high, one below both is a low, so the type is unambiguous and flat or one-slope stretches invent nothing — and refined with a three-point parabola around the peak, which gives a time to the minute and a corrected height. The series edges are never extrapolated.
+ Frontend: both pop-up builders (`buildLocationPopup`, `buildGridPointPopup`) write only an empty `[data-tide-slot]` carrying the point; `MapView` fills it on `popupopen` with the hour the pop-up itself shows, so a click that never happens costs no request. `loadPointTide` caches one promise per rounded point and hour, including in-flight requests, and a failed load is not remembered. The block reads `Tide · above MSL`, then the selected hour's height, then the last, next and following low/high with their times as local `HH:mm` (the fourth reading is omitted when `next_extreme_after` is null): metres in the metric display, feet in the imperial one. The current row reads `now` for the current hour and otherwise the same label as the pop-up's 🕒 row. Marker shapes are the triangles `▲`/`▼` in the single accent `#cbd5e1`, `aria-hidden` because the words carry the meaning, never the emoji arrows. A point with no tide leaves the rest of the pop-up untouched rather than showing an error.

# versioning (SCRUM-91)
the app version follows the release version (semantic versioning, e.g. 0.2.0 ↔ release/tag v0.2.0)
+ Single source of truth: `VERSION` file in the project root (plain `MAJOR.MINOR.PATCH`, no "v").
+ Backend reads it for the FastAPI app version (`/docs`) and returns it from `GET /api/health` as `version`.
+ Frontend reads it at build time (Vite `__APP_VERSION__`) and shows it in the navbar as `vX.Y.Z-<hash>`.
+ Build hash (SCRUM-159): the displayed version appends the short commit hash (`git rev-parse --short HEAD`), so the navbar badge and `GET /api/health` identify the exact build (`0.8.2-2af202f`). `VERSION`, `frontend/package.json` and release tags stay plain `X.Y.Z` / `vX.Y.Z`; the hash is build metadata passed as the `GIT_SHA` Docker build arg by `scripts/rebuild-container.sh`, with local builds falling back to git and a build without a hash showing plain `X.Y.Z`.
+ User-testing builds (SCRUM-159): a build requested for testing bumps the PATCH digit as well as adding the hash, so it never shares a version with a release; it is not a release, so it needs no release notes or tag.
+ `frontend/package.json` `version` must match `VERSION`; tests fail if they differ.
+ For every release: update `VERSION` and `frontend/package.json` to the release number before tagging `vX.Y.Z`.
+ Release notes (SCRUM-130): every release requires release notes saved in the `release-notes/` directory as `x-x-x.md` (e.g. `0-4-0.md`, replacing dots with hyphens) committed alongside the version bump and used when publishing the release on GitHub.
+ Container rebuild (SCRUM-132): whenever a merge to `develop` or `master` or a version bump is done, `scripts/rebuild-container.sh` must be executed to rebuild the Docker image and restart the local container on port 5005 for user verification.

# performance
the application should be respond to users request within 3 seconds
+ Startup (SCRUM-284): the app loads its config, the saved locations and the wave land mask concurrently (`Promise.all` in the frontend, `asyncio.gather` in the backend lifespan) instead of one after another, so the first screen no longer waits for the sum of the requests. A test holds one response open and asserts the rest still arrive.
+ Land mask (SCRUM-273): `land_mask.preload()` runs in a worker thread (`asyncio.to_thread`) during startup instead of parsing the mask on the event loop; peak resident memory was measured at 123.4 MB, which fits the 512 MiB Cloud Run limit with the existing asset.
+ Upstream connections (SCRUM-285): NWS calls use the shared pooled `httpx.AsyncClient` (`open_meteo.shared_client()`) with their own headers instead of a client per request, and retry `httpx.TransportError` within the same budget, so a point pop-up reuses its connection to `api.weather.gov`.
+ Long series (SCRUM-286): the tide service fetches only the UTC days it is missing, as contiguous ranges, instead of refetching the whole window around the requested hour.
+ One-day writes and reader-friendly SQLite (SCRUM-274): a day's grid is committed once, and WAL lets a read continue while a write is in flight.
