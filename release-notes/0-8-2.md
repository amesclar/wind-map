# Release Notes - v0.8.2

Release v0.8.2 is a patch release for Open-Meteo quota exhaustion. Previously, once the daily
request limit was reached, the wind gradient and barbs silently disappeared while the rest of the
map kept working. The app now explains what happened and when data should return.

---

## Fixes

### Quota exhaustion is reported instead of silently dropping the wind layer (SCRUM-170)
- **Backend:** after the existing retries, a persistent Open-Meteo `429` raises a dedicated
  `QuotaExceededError` carrying the reset instant from `X-RateLimit-Reset` (epoch), falling back to
  `Retry-After` seconds. `GET /api/weather/grid` returns **503** with
  `{code: "open_meteo_quota_exhausted", message, reset_at}` and a `Retry-After` header. Other
  upstream failures keep the existing 502 response, and no upstream body or host detail is exposed.
- **Frontend:** `ApiError` retains the structured JSON `detail`; only the quota marker is treated as
  exhaustion, so ordinary grid failures still follow the console-error path. The new warning dialog
  explains that the wind barbs and colour gradient cannot load and names the reset time in the
  user's timezone (for example `4:00 PM PST`), with a generic message when upstream sends no reset
  time.
- **Once per window:** `App` remembers the `reset_at` it has already warned about, so panning,
  zooming or retrying after dismissal does not reopen the dialog for the same quota window. A later
  reset time is a new window and can warn again.
- Saved locations, units and preferences are unaffected. A later pan or view change retries the grid
  normally; there is no automatic countdown timer.

## Compatibility
- No schema, API or dependency changes. Saved locations, map settings, units and forecast caches are
  untouched.
- Successful grid responses and all export paths are unchanged.

- Frontend: 362 tests across 36 files, coverage 94.39% statements / 86.50% branches / 92.87% functions
