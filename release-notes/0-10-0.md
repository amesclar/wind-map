# Release Notes - v0.10.0

Release v0.10.0 is the first version that runs on Google Cloud Run. The app is now deployed
automatically on every merge into `develop`, protected by the shared password, with its SQLite
database replicated to a bucket. It also adds in-app feedback that files a Jira issue, and fixes the
two defects that surfaced once the deployment was live: the wind layer disappearing when zoomed out,
and deploys silently detaching the CARTO key and the Jira token.

---

## Deployment on Google Cloud Run (SCRUM-134, SCRUM-135, SCRUM-136, SCRUM-189)

- **Image:** built for `linux/amd64`, tagged `VERSION-<sha>` and `latest`, pushed to Artifact Registry.
- **Access:** HTTP Basic Auth with one shared password from Secret Manager. The username is ignored;
  unauthenticated requests get `401` while `/api/health` stays public for the smoke test.
- **Persistence:** SQLite is replicated to `gs://wind-map-litestream-wind-app-515017` with Litestream.
  One instance, CPU always allocated. A fresh instance restores the database before serving.
- **Provisioning:** `scripts/gcp-provision.sh` creates the bucket, the secrets, the runtime service
  account and its IAM bindings, and verifies them by impersonation.
- **Automatic deploys:** `.github/workflows/deploy-cloud-run.yml` builds, pushes and rolls the service
  on every push to `develop`, then fails the run unless `/api/health` reports `status: ok`.
  Authentication is keyless through Workload Identity Federation; no service account key exists.

## In-app feedback (SCRUM-179)

- A top-bar button opens a form that files a bug or task in Jira under `SCRUM`, labelled
  `in-app-feedback`. It is enabled only when `JIRA_BASE_URL`, `JIRA_EMAIL` and `JIRA_API_TOKEN` are
  all present, and the button stays hidden otherwise. Requests are rate-limited per client IP.

## Fixes

### The wind layer disappeared when zoomed out (SCRUM-192)

- **Symptom:** at low zoom the wind barbs and gradient vanished; a 30 x 30 view returned `502`.
- **Root cause:** the backend put all 900 grid coordinates into one Open-Meteo query string — about
  16 KB. Open-Meteo answers `414 Request-URI Too Large`, so the whole grid request failed.
- **Fix:** the grid is fetched in sequential batches of at most 150 points (~3.3 KB each) and merged,
  preserving point order. A 900-point view is now six requests; smaller views still cost one. The
  batches run one at a time because the free tier allows one concurrent request per IP.
- **Tests:** chunking for current and hourly data, the single-request path at the limit, and a
  30 x 30 endpoint test asserting 900 points across six upstream calls.

### Deploys dropped the CARTO key and the Jira token (SCRUM-190)

- **Symptom:** a manual `gcloud run services update` that attached `CARTO_API_KEY` and
  `JIRA_API_TOKEN` was silently reverted by the next merge, so the map lost its basemap and the
  feedback button disappeared.
- **Root cause:** the deploy step named only `APP_PASSWORD` in `--set-secrets`; every deploy rebuilt
  the service without the other two.
- **Fix:** one `--set-secrets` flag lists all three secrets, and `--set-env-vars` carries
  `JIRA_BASE_URL` and `JIRA_EMAIL`. `scripts/gcp-provision.sh` now creates and grants the Jira token
  too, and a test pins the workflow so dropping a secret again fails CI.

## Compatibility

- **API and data:** unchanged. No endpoint, schema, settings key or stored preference is touched; the
  grid response keeps its shape and gains no fields.
- **Configuration:** the deployment now expects `CARTO_API_KEY` and `JIRA_API_TOKEN` in Secret
  Manager. `gcloud run deploy` fails when a referenced secret does not exist, so run
  `scripts/gcp-provision.sh` before the first deploy. Without a CARTO key the map falls back to the
  OpenStreetMap tiles; without the Jira trio the feedback button stays hidden.
- **Dependencies:** none added or upgraded.
