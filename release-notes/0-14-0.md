# Release Notes - v0.14.0

This release puts a second basemap on the map and makes the tide block honest. Google's satellite
imagery arrives as a landscape layer with roads and labels over it, and the export button explains
why it cannot capture it. Tides now admit when they cannot be loaded and stay off land, and the two
developer changes make every agent's Jira activity attributable.

---

## Changes

- **Google Satellite basemap (SCRUM-311):** Map Settings gains a sixth choice, and it is not a
  street map. The layer draws Google's satellite imagery as the `satellite` map type with the
  roadmap layer over it for roads, place names and water labels, in the same hybrid look the Google
  Maps app uses; plain `mapType: hybrid` is not a thing the Map Tiles API accepts, so the layer is
  the two together. Google's white logo sits at the bottom left of the map as their terms require.
  The key never reaches the browser: `GET /api/map/google-session` on our backend exchanges it for a
  short-lived session and returns only that, and tiles are read from
  `tile.googleapis.com/v1/2dtiles/`. Export is disabled while this is the base map — Google's terms
  do not allow capturing its tiles — and the export button now says so instead of failing quietly.
  The option is hidden entirely when the server has no key (`google_satellite_enabled` in
  `/api/config`), so a self-hosted instance without Google credentials sees the five map types it
  can actually draw. Barbs, chevrons, waves, seamarks and your saved locations draw over it as over
  any other base.

- **A tide block that admits failure (SCRUM-316):** a tide request that errors used to leave the
  card silently short, which looked exactly like a point with no water. The card now says
  `Tide unavailable` in its place, while a point with no tide at all still shows nothing extra.

- **No tides on land (SCRUM-317):** Open-Meteo's marine model snaps a shore request to its nearest
  sea cell — 48.24, -122.74 was answered as a cell about 4 km offshore — so a barb on the beach or
  inland showed a full tide block. Each point is now tested against the elevation service with the
  same 0.5 m threshold the current chevrons use. A land point makes no marine request at all; the
  verdict is cached for the usual 30 minutes, and a failed elevation lookup keeps the tide rather
  than hiding real water.

- **Cheaper pans (SCRUM-267):** the wind grid samples sit on a lattice anchored at 0° instead of on
  the viewport edges, so every view of one zoom asks for the same coordinates, and a pan now
  fetches only the strip it revealed while reusing the cached rows around it. On a 10 × 10 view a
  0.4° pan costs 10 of its 100 points instead of all 100. The current and wave layers share the
  same reuse.

## For developers

- **The deploy can read the map key (SCRUM-315):** the Cloud Run deploy step now injects
  `GCP_MAP_KEY`, and `scripts/gcp-provision.sh` creates or versions the secret and grants the runner
  access to it. Without the binding a deploy fails instead of quietly shipping an instance with the
  basemap hidden.

- **Agents write Jira as themselves (SCRUM-310, SCRUM-313):** every agent-issued Jira write goes
  through `scripts/jira_agent.py` on a service account, and `--key-variable` lets each bot use its
  own key. Ticket history now shows whether Freebuff or Kiro acted, and reads still use whatever
  account you are signed into.

---

**Upgrade notes:** no schema or data change. Production needs `GCP_MAP_KEY` in Secret Manager with
`wind-map-runner@wind-app-515017` holding `roles/secretmanager.secretAccessor`; that binding is now
in place, so the basemap appears as soon as this release is deployed. A hard reload clears a cached
old build if the map settings look unchanged.
