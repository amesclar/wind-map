# Release Notes - v0.9.0

Release v0.9.0 adds ocean currents to the map (SCRUM-137). A chevron layer shows where the surface
water flows and how fast, on the same forecast-time track as the wind — so a passage can be planned
with both fields on screen at once. The release also retries transient connection failures instead of
failing a grid request, holds one pooled HTTP connection for upstream calls, and refreshes the docs.

---

## What's New

### Ocean currents (SCRUM-96, SCRUM-99, SCRUM-100, SCRUM-98)
- **The field:** surface current speed and direction from the Open-Meteo Marine API
  (`ocean_current_velocity`, `ocean_current_direction`), provided by MeteoFrance SMOC through
  Copernicus Marine — global, about 8 km, hourly. Currents are **independent of the selected weather
  model**: one field with its own 240-hour horizon, so switching between Best Match, ECMWF, GFS and
  ICON leaves the water unchanged.
- **Two new endpoints:** `GET /api/currents/grid` returns the current for a bounding-box grid, and
  `GET /api/currents/point` a 240-hour series for one coordinate. Both take the same optional,
  hour-aligned `time` as the wind grid; an hour past the horizon is a 422 naming the limit. Grid
  points on land are left out (an inland box answers `{"points": []}`) and are cached along with the
  water ones, so panning inland does not repeat the upstream call. Responses are stored per hour in
  the new `grid_currents_cache` table (schema v4).
- **Chevrons on the map:** each point is drawn as a chevron pointing where the water flows, coloured
  by tier — light below 0.5 kt, moderate 0.5–1.5 kt, strong 1.5–3 kt, extreme 3 kt and above. Only
  sea points get a glyph, so the land stays readable. Chevrons follow the forecast-time selector
  (its own 240-hour window), are capped at 120 points per view, cancel in-flight requests when you
  pan or change hour, and fail quietly: a currents outage never breaks the wind layers.
- **Click for detail:** clicking a chevron shows its speed in your units, compass direction, where it
  flows toward, the source and the selected hour — with no extra request.
- **Controls:** a `Water Currents` toggle in Map Settings, independent of both wind layers, default
  **off**, and persisted so it survives a reload. With it on, a compact key at the map's top-left
  lists the four tiers with their ranges in your speed unit, generated from the same tier table as
  the chevrons.
- **Quota and retries:** marine calls use the shared Open-Meteo client, so `Retry-After` handling and
  the quota `503` (`open_meteo_quota_exhausted` with its reset instant) behave exactly as on the wind
  grid.

### Reliability and performance (SCRUM-176, SCRUM-174)
- **Transient failures are retried:** the shared client's retry loop now also covers transport errors
  (connect failures and timeouts) inside the same budget, so a dropped TLS connection retries
  immediately instead of surfacing as a 502.
- **One pooled connection:** a single `httpx.AsyncClient` per event loop is reused across requests,
  so panning and hour stepping keep their TCP/TLS connection; it is closed on shutdown.
- **Faster grid cache reads** and a leaner export hook.
- **Static assets resolve from a build index:** no request path is joined onto the filesystem, so a
  crafted URL cannot reach outside the build output.

## Compatibility
- **API:** no breaking changes. The weather endpoints, their responses and CORS behaviour are
  unchanged; the currents endpoints are additive.
- **Data:** saved locations and preferences are untouched. Schema v4 creates `grid_currents_cache`;
  as with earlier upgrades, only refetchable cache tables are recreated.
- **Dependencies:** no new backend or frontend packages. The currents layer is plain SVG, like the
  wind barbs.
- **Exports:** map export is unchanged — currents are not included in captured images in this
  release.
